The **Network Egress** page (route `/edr/network`, the **Networks** tab in the Endpoint sidebar) answers one question with no reconstruction step: *which application on this Mac talked to which destination, over which port, and how much data moved.* It is built entirely on the [`net_flow`](/macos-collector/event-data-model#network-payload-net-flow) event — outbound TCP flows captured by the **NetworkExtension** content-filter (`Hilt.EDRApp.NetFilter`) with an `lsof` socket poller as the always-available fallback, and **external-only by design**.

On Linux you see "pid 4821 connected to 142.250.80.14:443" and then spend the rest of the investigation figuring out *what app that was*. On macOS the kernel already resolved the flow's audit token back to the responsible application, so every `net_flow` row arrives stamped with `bundle_id` — the owning app — alongside the [code-signing trust](/dashboard/endpoint/foundation#why-endpoint-kernel-telemetry-is-different) carried on every event. The folding, the trust verdict, and the byte counts are all properties of the flow. This page is what that buys you.

<Note>
Network telemetry is **external-only**. Loopback (`127.0.0.0/8`, `::1`) and link-local traffic are never emitted — see [External-only network flows](/macos-collector/event-coverage#external-only-network-flows). Every row on this page is data leaving the Mac.
</Note>

## KPI strip

A four-tile summary sits at the top, scoped to the selected endpoint and time range. Representative live figures from one host over the window:

| KPI | Value | What it counts |
| :-- | :-- | :-- |
| **Total flows** | 208,224 | `net_flow` rows in range |
| **Distinct destinations** | 1,874 | unique `dst_addr` values contacted |
| **Distinct apps** | 28 | unique `application_id` groups that opened a socket |
| **External %** | 100% | all flows are off-host by design |

The strip is the shape of the host's egress at a glance: 28 apps fanning out to 1,874 destinations across 208k flows. The moment one of those numbers moves — a new app appears, the destination count jumps — it is visible before you open a single panel.

## Connection graph

The centerpiece is a three-tier connection graph: **host → application → destination**. The selected Mac sits at the center, every application that opened a socket radiates out as a node, and each app's destinations cluster beyond it. Edge thickness encodes flow volume; node size encodes fan-out.

The graph's defining behavior is **application folding**. A modern macOS app is not one process — Google Chrome alone runs `Google Chrome Helper`, `Google Chrome Helper (GPU)`, and `Google Chrome Helper (Renderer)` as separate `comm` values, each opening its own sockets. Grouping by raw process name scatters one browser across a dozen meaningless rows. The page groups by **`application_id`** instead, using Apple's responsible-process model: every helper's `responsible_pid` resolves to the owning app, so all of those helpers fold back into a single **Google Chrome** node. You see the app a human ran, not the transient helpers the OS spawned.

| Tier | Node | Backed by |
| :-- | :-- | :-- |
| **Host** | the selected Mac | `device_name` (100% of rows) |
| **Application** | the owning app, helpers folded in | `application_id` / `application_display_name` via `responsible_pid` |
| **Destination** | a contacted `dst_addr`, enriched to a hostname | `dst_addr` + reverse-DNS / SNI enrichment |

Clicking a host edge re-centers; clicking an application node opens the per-app drill-down below; clicking a destination shows every app that reached it.

<Note>
Folding happens at enrichment time, so it is identical across the graph, the tables, and any SQL you write. `GROUP BY application_id` and the page agree by construction.
</Note>

## Per-app drill-down

Selecting an application opens its full egress profile — the depth this page exists for. Instead of "Chrome talked to the internet," you get **exactly which destinations**, resolved and attributed:

| Column | Contents |
| :-- | :-- |
| **Destination** | resolved hostname (reverse-DNS) with the raw `dst_addr` beneath it |
| **Network owner** | the ASN / organization that owns the address block (e.g. `Google LLC`, `Amazon AWS`, `Cloudflare`) |
| **Port** | `dst_port` with its service label — `443 · HTTPS`, `9440 · ClickHouse/TLS`, `5228 · Google GCM` |
| **Flows** | `count()` of `net_flow` rows to that destination |
| **Bytes** | `sum(bytes_sent)` / `sum(bytes_recv)` — byte counts are present on every flow |

Two lenses sit at the top of the drill-down and are **first-class**, not buried in a filter menu:

- **Signed vs. unsigned filter.** Because `code_signature` rides on every flow, "which unsigned app is talking out" is one toggle. Flip it to `unsigned_or_invalid` / `adhoc` and the graph collapses to exactly the binaries with no trusted identity that are nonetheless reaching the network — the single highest-value egress question on the platform, and one the Linux collector cannot express.
- **Interface lens.** Flows are grouped by the interface that carried them, so the *path off the Mac* is legible:

| Interface | Meaning | Why it matters |
| :-- | :-- | :-- |
| `en0` / `en1` | Wi-Fi / Ethernet | normal egress |
| `awdl0` | Apple Wireless Direct Link | **AirDrop** and peer-to-peer — a sideband exfil path |
| `utunN` | tunnel interface | **VPN** traffic — egress leaving through a tunnel |
| `pdp_ip0` | cellular data | traffic on **cellular**, off the corporate network |

<Warning>
DNS names and ASN owners come from **reverse-DNS / SNI enrichment** applied after capture — `net_flow` itself records the 5-tuple, byte counts, and responsible app, never DNS query contents. A destination that fails to resolve is shown as its raw `dst_addr`; this is a resolution miss, not a gap in attribution.
</Warning>

## Top ports

Egress port distribution for the host, with friendly service labels resolved on top of the raw `dst_port`:

| Port | Service | Flows | Reading |
| :-- | :-- | :-- | :-- |
| 443 | HTTPS | ~180,033 | the overwhelming majority — normal app/web traffic |
| 9440 | ClickHouse / TLS | — | analytics / database TLS egress |
| 5228 | Google GCM | — | Google Cloud Messaging push channel |
| 4070 | Spotify | — | Spotify's media control channel |

HTTPS on 443 dominates (~86% of all flows), which is expected: nearly every modern app speaks TLS. The value is in the **non-443 tail** — a port like 9440 or 4070 immediately attributes itself to an app and a destination, so an unexpected port is one click from "which app, signed by whom, opened it."

### Protocol mix

`net_flow` records outbound **TCP** flows. The protocol mix panel breaks the flow population down by destination-port service class — HTTPS, push/messaging channels, database/TLS, media — so the host's egress reads as a handful of named channels rather than a wall of port numbers.

## Top talkers

The top-talkers table ranks applications by flow volume and shows each one's **destination fan-out** — how concentrated or sprawling its egress is. Fan-out is as diagnostic as raw volume: a tool with millions of flows to a handful of endpoints is a busy client; a process with moderate flows fanning out to thousands of destinations is a scanner, a crawler, or a browser.

| Application (`application_id`) | Flows | Distinct destinations | Profile |
| :-- | --: | --: | :-- |
| **Cursor Helper (Plugin)** | 62,946 | 258 | heavy IDE/AI traffic, moderate fan-out |
| **Google Chrome Helper** | 55,087 | 1,357 | the browser — enormous fan-out across the web |
| **claude** | 29,573 | 11 | high volume, *tight* fan-out — a focused API client |
| **Slack** | — | — | collaboration, steady push + media |
| **Spotify** | — | — | media streaming, port 4070 + 443 |
| **Notion** | — | — | document sync |
| **Discord** | — | — | chat + voice |

The contrast between **claude** (29,573 flows / 11 destinations) and **Google Chrome Helper** (55,087 flows / 1,357 destinations) is the whole point: similar order-of-magnitude volume, wildly different shapes. One is an API client hammering a stable set of endpoints; the other is a browser reaching the entire web. Reading flow count without fan-out would conflate them.

### Per-app destination breakdown

Expanding a top talker reveals the same destination table as the drill-down — each app's exact endpoints, resolved and attributed. This is the depth the page guarantees: not "these apps are talking out" but "**this** app reached **these** hosts, on **these** ports, moving **this** many bytes."

```sql
-- Per-application destination breakdown for one Mac, helpers folded in.
-- Grouped by application_id so Google Chrome Helper (Renderer), (GPU), etc.
-- all collapse into Google Chrome — exactly what the drill-down renders.
SELECT
    application_display_name,
    dst_addr,
    dst_port,
    count()              AS flows,
    sum(bytes_sent)      AS out_bytes,
    sum(bytes_recv)      AS in_bytes,
    any(code_signature)  AS trust
FROM endpoint_events
WHERE event_type  = 'net_flow'
  AND device_name = 'Zin''s MacBook Pro'
  AND event_time >= now() - INTERVAL 24 HOUR
GROUP BY application_id, application_display_name, dst_addr, dst_port
ORDER BY flows DESC
LIMIT 50;
```

Swap the final filter for `code_signature IN ('unsigned_or_invalid', 'adhoc')` and the same query becomes *"which untrusted binary is exfiltrating, and to where"* — the signed-vs-unsigned lens as raw SQL.

## What this maps to in ATT&CK

Egress attribution is the detection substrate for exfiltration and C2 techniques. The page's per-app, per-destination, per-byte view is what lets you separate a normal sync client from data leaving the building:

| Technique | What this page surfaces |
| :-- | :-- |
| [T1048 — Exfiltration Over Alternative Protocol](https://attack.mitre.org/techniques/T1048/) | a non-443 port, or an `awdl0` / `utunN` / `pdp_ip0` path, attributed to a specific app |
| [T1567 — Exfiltration Over Web Service](https://attack.mitre.org/techniques/T1567/) | high `bytes_sent` from an unexpected — especially `unsigned_or_invalid` — app to a cloud destination |

Because trust and owning-app identity are on every flow, "an `unsigned_or_invalid` binary moved 4 GB to an AWS endpoint over cellular" is a single row here, not a multi-source correlation.
