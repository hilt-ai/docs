The **Endpoint** section is the macOS half of the platform. Every page in it is a different lens on the same stream: the typed kernel events the [macOS collector](/macos-collector/event-data-model) emits from Apple's Endpoint Security (ES) framework and lands in the `endpoint_events` table. Where the **Cloud** section shows what Linux workloads do, the Endpoint section shows what a person's Mac does — and it shows it with a level of attribution the kernel gives you for free on macOS and nowhere else.

This page explains the foundation the rest of the section stands on. Read it once, and every other Endpoint page reads faster.

---

## Why endpoint kernel telemetry is different

On Linux, a kernel event is a syscall: a pid opened a path, a pid connected to an address. To learn *who* did it — which signed application, trusted by whom — you have to reconstruct it after the fact, and usually you cannot.

On macOS, the kernel already knows. Apple's Endpoint Security framework hands ESensor the **code signature** and the **responsible application** on every single message. The collector promotes both to first-class columns, so every row — a file open, a network flow, a process exec — arrives already stamped with three things:

| It tells you | Column(s) | Why it matters |
| :-- | :-- | :-- |
| **Who signed this binary** | `signing_id`, `team_id`, `cdhash` | The exact vendor identity and a cryptographic fingerprint of the running code. |
| **Whether to trust that signature** | `code_signature` | A four-tier verdict — `platform`, `developer_id`, `adhoc`, `unsigned_or_invalid` — on *every* action, not just on launch. |
| **Which application is responsible** | `application_id`, `application_display_name`, `responsible_pid`, `session_id` | The owning app, with helper processes folded back to it, and the device name on 100% of rows. |

That is the thesis of the entire section: **trust and identity are not a lookup you perform later, they are a property of the event.** It turns questions that are impossible on Linux into a single filter — *"which `unsigned_or_invalid` binary read `~/.ssh`?"*, *"which application, signed by which team, opened that connection?"* — and every page below is a pre-built answer to one of those questions.

```sql
-- The query that defines the section: trust, on any action, on any page.
SELECT event_time, device_name, application_display_name, comm,
       signing_id, team_id, code_signature, event_type, filename, dst_addr
FROM endpoint_events
WHERE code_signature IN ('unsigned_or_invalid', 'adhoc')
ORDER BY event_time DESC;
```

<Note>
Every event also carries `device_name` (e.g. `Zin's MacBook Pro`) on 100% of rows, so there is never a host-inventory join between an event and the human-readable machine that produced it.
</Note>

## The pages

The section splits into three families — **what runs**, **what leaves**, and **what is at risk** — plus the raw streams that feed them.

| Page | Question it answers | Built on |
| :-- | :-- | :-- |
| [Persistence](/dashboard/endpoint/persistence) | What installed itself to survive a reboot? | `btm_add` |
| [Tamper Detection](/dashboard/endpoint/tamper) | What tried to weaken the Mac's defenses — or the agent? | `xattr_*`, `signal`, profiles |
| [Credential & Privacy](/dashboard/endpoint/credential-privacy) | Who reached for the Keychain, or turned on the camera or mic? | `file_open`, TCC, privacy |
| [Removable Media](/dashboard/endpoint/removable-media) | What got plugged in, and what was written to it? | `mount`, `file_*` on `/Volumes` |
| [Network Egress](/dashboard/endpoint/network-egress) | Which app talked to which destination, and how much? | `net_flow` |
| [ATT&CK Matrix](/dashboard/endpoint/attack-matrix) | What is our coverage of the MITRE techniques? | all detections |
| [Process Lineage](/dashboard/endpoint/process-lineage) | Who spawned what? | `exec`, `fork` |
| [Credential Access](/dashboard/endpoint/credential-access) | Which process touched which secret? | `file_open` on credential paths |
| [Activity](/dashboard/endpoint/activity) | What is happening on this Mac right now? | all event types |
| [Files](/dashboard/endpoint/files) | What is the file activity, and where did each file come from? | `file_*`, provenance |

The first five are detection-and-summary pages built on the [finding catalog](/dashboard/endpoint/foundation#findings-and-severity); the last five are exploration pages built directly on the raw `endpoint_events` stream. The ATT&CK Matrix ties them together.

## Shared layout

The five detection pages — Persistence, Tamper, Credential & Privacy, Removable Media — share one layout, so once you can read one you can read all of them.

- **Agent header** — a status bar for the selected Mac: device name, risk level, last-seen time, **Endpoint Security** and **Network Extension** run state, policy version, and live finding/event counts. It is how you know, at a glance, that the sensor is healthy and current.
- **Summary cards** — one card per activity group, each showing the group's finding count and worst severity, so the shape of a page is legible before you read a single row.
- **Timeline** — a 60-minute, per-minute chart of findings. Flat is calm; a spike is a burst worth opening.
- **Severity / Status filters** — narrow to a severity (`critical` → `info`) or to how the agent responded (`blocked`, `alerted`, `logged`).
- **Findings table** — a grouped, collapsible table: **Time · Type / Target · App · Severity · Status**. Near-identical findings (the same rule, app, and target) collapse into one row with an `N×` badge you can expand, so a noisy updater rewriting the same plist 700 times reads as one line, not seven hundred.
- **Finding detail** — selecting a row slides in a six-part breakdown: **What happened · Process responsible · What was touched · Why it matters · Evidence · Recommended action**. The "Process responsible" panel is where the code-signing verdict and the owning application live.

### Findings and severity

Severities rank the *likelihood of harm*; statuses record *what the agent did about it*.

| Severity | Meaning |
| :-- | :-- |
| **Critical** | Likely harmful — investigate first |
| **High** | Suspicious and worth prompt attention |
| **Medium** | Noteworthy but less urgent |
| **Low** | Minor or informational |
| **Info** | Routine activity, recorded for completeness |

| Status | Meaning |
| :-- | :-- |
| **Blocked** | The action was actively stopped on the device (an AUTH deny) |
| **Alerted** | Flagged for review |
| **Logged** | Recorded for the record |

Because the verdict columns ride on every event, severity is rarely about the action alone — a launch item registered by a `developer_id` updater is `info`, the same launch item registered by an `unsigned_or_invalid` binary is `high`. The trust tier *is* the severity input.

## Selecting an endpoint

The detection pages and the exploration pages resolve to a single Mac. The endpoint picker lists every device reporting telemetry with its name, host ID, total event count, and last-seen time; your choice is remembered across pages and switchable from the **Change** control in the header. Pages that aggregate the whole fleet (the [ATT&CK Matrix](/dashboard/endpoint/attack-matrix), the [Files](/dashboard/endpoint/files) fleet roster) open fleet-wide and drill into one host on click.

## What this section never sees

The same boundary the collector draws holds across every page: this is **metadata, not content**. The Endpoint section shows *that* a binary opened a file, signed by whom, on behalf of which app — never *what was in* the file. It does not capture file contents, packet payloads, DNS query contents, keystrokes, screen contents, process memory, or environment variables. See [What the collector does not capture](/macos-collector/event-data-model#what-the-collector-does-not-capture) for the full boundary.
