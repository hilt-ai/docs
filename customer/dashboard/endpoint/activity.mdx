Every other Endpoint page is an *opinion*. [Persistence](/dashboard/endpoint/persistence) decides what counts as a launch item worth surfacing; [Network Egress](/dashboard/endpoint/network-egress) decides which flows are interesting; [Files](/dashboard/endpoint/files) decides how to roll opens up into provenance. **Activity** holds no opinion. It is the unprojected `endpoint_events` stream for one Mac, rendered as it arrives — the firehose lens under the curated pages.

You come here for two reasons: to **confirm a hypothesis against actual rows** — "the finding says Chrome opened this; show me the literal event" — or to **watch a Mac in real time** during an investigation, the way you would tail a log on a box you suspect. Everything above this page is a query with a `WHERE` clause already applied. Activity is what those queries run against. See the [kernel foundation](/dashboard/endpoint/foundation) for the model the whole section shares.

<Note>
Even the firehose is attributable. Because `code_signature` and `application_display_name` ride on [every row](/macos-collector/event-data-model#code-signing-identity-every-event-the-macos-differentiator), the raw stream is never anonymous noise — a single unfiltered table still tells you *which signed application did each thing*. That is the macOS difference, visible even with no projection applied.
</Note>

## Page layout

Activity resolves to **one Mac** — it is a host-scoped, not a fleet, view. The header is deliberately thin so the stream dominates the screen.

- **Host selector** — the same endpoint picker used across the section ([selecting an endpoint](/dashboard/endpoint/foundation#selecting-an-endpoint)). Your choice persists across pages; switch from the **Change** control. Every row below is one device's `device_name`.
- **Summary cards** — one card per `event_type`, each a live count over the current window (see below).
- **Recent-events table** — the continuously refreshing tail of the stream, newest first.

The page does not have severity filters, timelines of *findings*, or grouped collapsing — those belong to the [detection pages](/dashboard/endpoint/foundation#shared-layout). Activity shows rows, not verdicts.

## Summary cards

A strip of cards sits above the table, one per `event_type` present on the host, each showing a live count. They are how you read the *shape* of a host's activity at a glance before scrolling a single row — a Mac mid-build looks different from a Mac mid-exfil.

The distribution is lopsided, and intentionally so. Here is the real `event_type` distribution on the reference Mac:

| `event_type` | `event_class` | Approx. count | Share |
| :-- | :-- | --: | --: |
| `file_open` | file | ~63.9M | ~95% |
| `file_unlink` | file | ~512k | ~0.8% |
| `exec` | process | ~455k | ~0.7% |
| `file_chmod` | file | ~323k | ~0.5% |
| `file_rename` | file | ~138k | ~0.2% |
| `fork` | process | ~103k | ~0.2% |

`file_open` alone is roughly **95%** of everything a Mac emits — opening files is what applications do all day. That single fact is why the collector filters so hard *before* shipping: framework loads, font and locale reads, cache churn, and preference-plist reads are dropped in userspace so the stream that reaches this page is the security-relevant remainder, not the raw kernel firehose. See [Agent filtering](/macos-collector/event-coverage#what-gets-filtered) for exactly what gets dropped and what is [never filtered](/macos-collector/event-coverage#what-is-never-filtered).

<Warning>
The counts here are post-filter. They are smaller than the raw kernel volume by design — what you are watching is already the curated remainder. `net_flow`, `btm_add`, `xattr_*`, `signal`, and `mount` appear when they occur; the first three of those are [never dropped](/macos-collector/event-coverage#what-is-never-filtered), so their absence over a window is genuine quiet, not filtering.
</Warning>

## Recent-events table

The body of the page is a live table that refreshes continuously, prepending new rows as events land and ordered newest-first by `event_time`. It is the literal tail of `endpoint_events` for the selected host.

| Column | Source | Meaning |
| :-- | :-- | :-- |
| **Time** | `event_time` | When the kernel observed the event. Authoritative timestamp is `wall_time_ns`; `event_time` is the queryable `DateTime64`. |
| **Type** | `event_type` | The specific event — `exec`, `file_open`, `net_flow`, etc. Color-keyed by `event_class`. |
| **Process** | `comm` + `code_signature` | The acting binary, badged with its trust verdict (`platform` / `developer_id` / `adhoc` / `unsigned_or_invalid`). |
| **Parent** | `parent_comm` / `ppid` | The spawning process, so a lineage is legible inline. |
| **User** | `username` (`uid`) | Who the action ran as (`root` is valid and common). |
| **Target** | *adapts by type* | The object of the event — see below. |

### The Target column adapts

There is no single "target" across event types, so the column renders the right field for each row:

| For these events | **Target** shows | Underlying column |
| :-- | :-- | :-- |
| `file_open`, `file_unlink`, `file_chmod` | The file path | `filename` |
| `file_rename` | `filename` → `dest_path` | `filename`, `dest_path` |
| `net_flow` | `dst_addr:dst_port` | `dst_addr`, `dst_port` |
| `exec` | The command line | `argv` |
| `signal` | The victim PID and signal | `target_pid`, `signum` |
| `xattr_set` / `xattr_delete` | `filename` (`xattr_name`) | `filename`, `xattr_name` |
| `btm_add` | The launch item path | `item_path` |
| `mount` | The mount point | `path` (via `attrs`) |

A file event shows a path; a network flow shows `dst_addr:dst_port`. One column, the correct subject for every row.

### Attribution rides along

Because the identity layers are on every event, each row also carries — visible inline or in the row's expansion — the **owning application** (`application_display_name`) and **signing identity** (`signing_id`, `team_id`). So even while you are watching raw, you can read a `net_flow` and immediately see it was `Google Chrome`, signed `developer_id` — or that the `file_open` on `~/.ssh/id_rsa` came from an `unsigned_or_invalid` binary with no team behind it. The firehose is attributable without leaving the page.

## Querying the same stream

The table is a thin window over a query you can run directly. The simplest form — the recent tail for one Mac — is what the page renders:

```sql
-- The recent-events table, in one query: the live tail for one Mac.
SELECT event_time,
       event_type,
       comm,
       parent_comm,
       username,
       code_signature,
       application_display_name,
       -- the adaptive Target: path for files, dst for flows, argv for exec
       multiIf(
         event_type = 'net_flow', concat(dst_addr, ':', toString(dst_port)),
         event_type = 'file_rename', concat(filename, ' -> ', dest_path),
         event_type = 'exec', argv,
         filename
       ) AS target
FROM endpoint_events
WHERE device_name = 'Zin''s MacBook Pro'
ORDER BY event_time DESC
LIMIT 200;
```

Because trust and identity are columns, narrowing the firehose to a hypothesis is one added predicate — `AND code_signature IN ('unsigned_or_invalid', 'adhoc')`, or `AND application_id = 'com.google.Chrome'`, or `AND event_type = 'net_flow'`. That is the whole argument of the section, made concrete: on Linux you would reconstruct the actor after the fact; here it is already on the row you are watching.

## How Activity relates to the other pages

Activity is the raw substrate; the rest of the section is projections of it. When a finding or a curated row raises a question, drop to Activity to see the literal events behind it.

| If you want to… | Use the curated page | Drop to Activity to… |
| :-- | :-- | :-- |
| See what installed itself to persist | [Persistence](/dashboard/endpoint/persistence) | Watch the `btm_add` row land in real time |
| Trace who spawned what | [Process Lineage](/dashboard/endpoint/process-lineage) | Confirm the raw `exec` / `fork` chain row-by-row |
| Track where a Mac is talking | [Network Egress](/dashboard/endpoint/network-egress) | See each `net_flow` with `dst_addr:dst_port` as it opens |
| Understand a file's history and origin | [Files](/dashboard/endpoint/files) | Read the underlying `file_open` / `file_rename` events |
| Verify a finding is real | any [detection page](/dashboard/endpoint/foundation#shared-layout) | Match it against the actual rows that produced it |

<Note>
Activity is metadata, like the rest of the section — it shows *that* a binary opened a file, signed by whom, on behalf of which app, never *what was in* the file. See [what the collector does not capture](/macos-collector/event-data-model#what-the-collector-does-not-capture).
</Note>
