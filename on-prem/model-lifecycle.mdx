The Model Lifecycle page shows the current state of the on-prem TRACE anomaly detection model and lets authorized administrators promote or roll back model versions. This page requires the **view audit** permission.

---

## Model status

The hero section at the top shows the current model state:

- **Active version**: the model version currently scoring events in production.
- **Shadow version**: a newer model version being evaluated side-by-side with the active model (if a training run has completed).
- **Training status**: whether a training run is currently in progress, and its progress.

---

## Health checks

A set of automated health checks that run after each model update to verify the new version is performing correctly:

- **Detection coverage**: whether the model detects the expected set of known-bad patterns.
- **False-positive rate**: whether the false-positive rate stays within acceptable bounds.
- **Latency**: whether inference latency remains within service-level targets.
- **Score distribution**: whether anomaly scores are distributed similarly to the previous model (no sudden drift).

Each check shows a pass/fail status and a brief explanation.

---

## Performance journey

A timeline visualization showing how model performance metrics have evolved across recent versions. Click a version marker to view its specific metrics. The most recent (current) version is selected by default.

---

## Update history

A table of recent model updates showing:

- **Version**: the model version identifier.
- **Status**: whether the update succeeded, failed, or is in progress.
- **Timestamp**: when the update was applied.
- **Changes**: a summary of what changed (e.g., retraining, feature additions).

---

## Promote and rollback

### Promote shadow to active

When a shadow model passes all health checks, you can **promote** it to become the active scoring model. This replaces the current active model. Promotion requires confirmation.

### Rollback

If the active model is misbehaving, you can **roll back** to the previous version (or the baked-in base model if no prior version exists). Rollback also requires confirmation and takes effect immediately.

Both actions require the **manage users** permission.
